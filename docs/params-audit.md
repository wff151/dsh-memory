## 三、参数合理性审查（发现 4 处不合理）

### 3.1 ⚠️ 短期记忆没有容量上限 —— 真问题

**数据**（今天实测）：

| 日期 | 新增短期记忆 |
|---|---|
| 2026-10-25 | **311 条** |
| 2026-10-26 | **143 条** |
| 累计 | **611 条**，261 KB |

**代码里搜不到任何 `maxItems` / `capacity`。**

增长来源：`autoRecordShort`（每条用户消息）+ `autoRecordAnswer`（每条回答）。
衰减每 6 小时跑一次，只按**权重**清，不按条数。

**后果**：
- 短期表无限增长 → 每次检索要遍历全部（已 611 条）
- 特征索引只取前 300 条 → **超过 300 的部分拿不到特征加成**
- 存储文件持续变大

**建议**：加一个 `shortMaxItems`（默认 2000 左右），超出时按"权重低 + 最老"归档。
这是当前最该修的一项。

### 3.2 ⚠️ `embeddingMinScore` 代码默认 0.3 太低

nomic 实测：相关中位 0.666 / 无关中位 0.616。
`0.3` 会把大量无关条目放进结果。

现在 profile 里已经改成 `0.62`，**但代码默认值还是 0.3** ——
别人装这个插件（不带 profile 覆盖）会踩这个坑。

**建议**：代码默认改成 `0.55`，并在注释里说明"不同模型尺度不同，需按实测调"。

### 3.3 ⚠️ `embeddingEnabled` 代码默认 `true`，但默认端口是错的

代码默认 `embeddingEnabled: true` + `baseURL: 127.0.0.1:1234` + `model: text-embedding-nomic-embed-text-v1.5`。

**新用户装完、没起服务 → 每 10 秒探测一次、每次失败退避**。
虽然有回退不报错，但**默认开着一个不可用的服务**不合适。

**建议**：代码默认改成 `false`。想用的人自己在设置页打开。
（"默认关闭、按需开启"也符合你之前说的"用的时候再开"。）

### 3.4 三处遗留常量该清理

`SHORT_MAX_CHARS` / `LONG_MAX_CHARS` / `ANSWER_MAX_CHARS` / `LONG_SUMMARY_CHARS`
在改成"存全文 + 摘要"之后已经不用了，但常量还在。
**不影响行为，但会误导后来改代码的人。**

## 四、分工建议

| 类别 | 谁调 | 理由 |
|---|---|---|
| 开关类（注入/落库/向量） | **用户** | 取决于个人偏好和使用场景 |
| 定时频率 | **用户** | 取决于使用强度 |
| 向量连接参数 | **用户**（有默认值兜底） | 取决于本机装了什么服务 |
| 摘要长度 | **用户** | 上下文预算 vs 信息完整的取舍 |
| 衰减曲线（lambda/threshold） | **我** | 改错会让记忆过早消失，且需要长期验证 |
| 检索打分的所有系数 | **我** | 每调一次都要跑 A/B，不适合暴露给用户 |
| 词表 | **我** | 与语言强相关，需要实测 |
| 容量上限 | **应做成配置**（现在没有） | 用户该能控制"短期库留多少条" |

## 五、最该做的三件事（按优先级）

| 序 | 事项 | 影响 |
|---|---|---|
| 1 | **加短期记忆容量上限**（配置项 `shortMaxItems`） | 防止无限增长；实测已 612 条 |
| 2 | **`embeddingEnabled` 代码默认改 `false`** | 新用户不会默认挂一个连不上的服务 |
| 3 | **`embeddingMinScore` 代码默认改 0.55** | 避免别人踩我踩过的坑 |

前两项是**行为问题**，第三项是**默认值问题**。

## 六、执行结果（2026-10-26 实施）

四项全部完成，并在过程中**发现一个更严重的隐藏 bug**。

### 6.1 修完的四项

| 项 | 改动 |
|---|---|
| 短期容量上限 | 新增 `shortMaxItems`（默认 **2000**），`decay.ts` 末尾按"权重低先走、同权重最老先走"裁剪 |
| `embeddingEnabled` | 代码默认 `true` → **`false`** |
| `embeddingMinScore` | 代码默认 `0.3` → **`0.55`** |
| 死代码 | 删掉 `SHORT_MAX_CHARS` / `LONG_MAX_CHARS` / `LONG_SUMMARY_CHARS` / `ANSWER_MAX_CHARS` |

### 6.2 ⚠️ 顺带挖出的隐藏 bug：**衰减后的权重从来没写回存储**

**原代码**：

```ts
if (archived.length > 0) {
  await store.replaceShortTerm(mode, remaining)
}
```

**只有当有条目被归档时才写回。** 于是一轮衰减里"没有任何条目达标"时，
**算好的新权重全部丢掉**，条目权重一直停在初始值。

**实测证据**（真实库，612 条）：

| 指标 | 值 |
|---|---|
| 权重最低 | **1.000** |
| 权重最高 | 1.900 |
| 低于归档阈值 0.15 的 | **0 条** |

**612 条里没有一条衰减过。** 我先前一直以为"衰减在跑"，其实它跑完什么都没留下。

这个 bug 的后果是连锁的：
- 权重永不下降 → `weight < 0.15` 的归档条件**永远不成立**
- 短期库只增不减（所以才有 612 条）
- 容量上限如果是唯一手段，就变成了**唯一**手段

**发现方式**：写容量测试时，第 6 项断言"权重按 exp(-0.05×10) 衰减"期望 0.6065、实际 1.0000。
**如果不测这一项，这个 bug 会一直存在。**

**修法**：只要权重有变化就写回，用"长度不等或任一权重变化"作判据，避免无意义的整表写入。

### 6.3 测试

`_tools/test-short-capacity.mjs`（11 项，全过）：

| # | 验证 |
|---|---|
| 1 | 超限后剩余 = maxItems |
| 2 | 归档条数正确 |
| 3 | 权重高的全部留下 |

| 5 | 同权重时保留最新的 |

### 6.4 关于 2000 这个值（用户的话）

> 「默认 2000 条，用户可以自己修改，其实两千条占用的上下文不多，影响的是检索数据，由用户自己决定。」

**这个判断是对的**，代码注释里也写了：短期投影每步只取固定几条
（状态 3 + 事件 3 + 关系 3），**条数上限不影响每步注入量**，
影响的是检索遍历量和特征索引覆盖（索引只取前 300 条）。

所以 2000 是"够宽但不会失控"的值，用户可按自己的检索需求调。
