# 短期记忆的两条容量触发（2026-10-26）

> 需求：除了"达到条数上限"，再加一条"占上下文百分之几"时归档。

---

## 一、默认值：**15%**

**依据**（实测 613 条 / 27331 tokens / 平均 44.6 tokens 条）：

| 窗口 | 15% 对应 | 换算条数 |
|---|---|---|
| 32k | 4800 tok | **≈ 107 条** |
| 64k | 9600 tok | ≈ 215 条 |
| 128k | 19200 tok | ≈ 430 条 |

**为什么不取更小**：5% 在 32k 上只有 35 条 —— 正常用一天就会反复触发，
等于把有用的近记忆一直扫掉。

**为什么不取更大**：20% 在 32k 上是 143 条，已经接近多数人的实际使用量，
和条数上限（2000）几乎重叠，两条触发就没区别了。

15% 落在"库明显偏大、但还没到病态"的位置。

---

## 二、⚠️ 口径必须先说清：算的是哪一个"占上下文"

这是设计里最容易搞错的地方。三种可能的度量：

| 度量 | 当前实测 | 32k 窗口占比 | 会不会随增长 |
|---|---|---|---|
| **A 全部正文** | 36458 tokens | **113.93%** | 会，随条数线性增长 |
| **B 每步投影** | 58 tokens | 0.18% | **不会**（固定 3+3+3） |
| **C 检索返回 top3** | 122 tokens | 0.38% | 随摘要长度 |

**选了 A（全部正文）**，理由：

1. **B 根本不能用** —— 投影是固定值（状态 3 + 事件 3 + 关系 3），
   条数从 100 涨到 10000，投影还是 58 tokens。
   **用它做触发条件等于永远不会触发，这个功能就是空的。**
2. **A 虽然不是"全进上下文"，但它诚实反映"库有多大"** ——
   而库越大，后果是实的：检索要遍历更多条、特征索引只取前 300 条覆盖不全。
3. C 是真正撑上下文的那部分，但它由查询决定，不是"库的状态"，
   拿它当容量触发会让同一个库在不同问题下时灵时不灵。

**所以代码注释和 UI 提示里都写明了**：
算的是「短期库**全部条目**的估算 token ÷ 上下文窗口」。

---

## 三、两条触发的关系

```
条数上限 shortMaxItems (2000)          ← 固定，不随模型变
窗口占比 shortContextSharePercent (15%) ← 随模型变，自适应
                    ↓
        取**更严**的那个（谁先满谁生效）
                    ↓
     按「权重最低先走，同权重最老先走」归档
```

**为什么需要两条**：
`2000 条` 在 1M 窗口的模型上永远不触发（2000 × 44.6 = 89200 tokens = 8.9% 占比）；
但在 32k 窗口上，2000 条就是 89% —— 早就该清了。
**只有按比例算，才能跨模型自适应。**

---

## 四、窗口大小从哪来

定时器是全局的、没有 session。所以从 `agent/inbox/claimed` 里顺手记：

```ts
const ctxWindow = agent.session.requestContext()?.contextWindow
if (typeof ctxWindow === 'number' && ctxWindow > 0) lastContextWindow = ctxWindow
```

**取不到时的行为**：`lastContextWindow = 0` → 占比触发**静默跳过**，
只走条数上限那条。

**这是刻意的**：不能退化成"永远不触发"（那等于没做），
也不能退化成"永远触发"（那会把记忆扫光）。

## 五、测试（`_tools/test-context-trigger.mjs`，15 项全过）

| # | 验证 | 结果 |
|---|---|---|
| 1–2 | 只配条数：按条数触发，标记 `items` | ✓ |
| 3–5 | 只配占比：按占比触发，标记 `context`，结果 ≈33 条（±3），报告裁剪前占比 30% | ✓ |
| 6–7 | 两条都配、占比更严：取占比（≈33 条），标记 `context` | ✓ |
| 8–9 | 两条都配、条数更严：取条数（50 条），标记 `items` | ✓ |
| 10–11 | **拿不到窗口：不裁剪**，标记 `none` | ✓ |
| 12 | 占比低于阈值：不触发 | ✓ |
| 13–14 | 裁剪保留高权重、裁剪后不超上限 | ✓ |

**回归**：`test-short-capacity.mjs` 11/11 仍全过；检索召回未变（top1 80% / top3 98%）。

---

## 六、配置

```yaml
shortMaxItems: 2000              # 条数上限
shortContextSharePercent: 15     # 占上下文窗口百分比上限
```

**两条都置 0 = 都不限制**（不推荐，库会无限增长）。

设置页在「设置 → 记忆 → 定时机制」，两个都能改。

---

## 七、可观测性

衰减结果里带了诊断字段：

```ts
contextShareBefore?: number      // 裁剪前占窗口的百分比
triggeredBy?: 'items' | 'context' | 'none'   // 哪条触发在起作用
```

日志会打印：

```
memory: decay archived 87 short-term item(s) (daily 80/context, work 7/items)
```

这样能直接看出"这次是条数还是占比把它清掉的"。

手动衰减工具（`brain_memory_decay`）也会回报触发原因 ——
但**它拿不到窗口**，所以那一步只走条数上限，占比由定时衰减负责。
