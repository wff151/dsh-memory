# 突破：摘要截断导致的关键信息丢失

> 时间：2026-10-26
> 一句话：**检索只看摘要，而摘要会截掉关键信息——这是 33% 完全找不到的真因。**

---

## 一、数据对比

按「够用就行」的口径（40 条不含名问法）：

| 口径 | 修前 | 修后 |
|---|---|---|
| **top1（模型直接拿到答案）** | 55% | **83%** |
| **top3（候选里有，模型能挑）** | 68% | **98%** |
| **完全找不到（rank=-1）** | **33%** | **3%** |

全量 100 问：

| 问法 | top1 | top3 |
|---|---|---|
| 含名·直接 | **100%** | 100% |
| 含名·场景 | **100%** | 100% |
| 含名·假设 | **100%** | 100% |
| **不含名·内容** | **83%** | **98%** |
| **总计** | **93%** | **99%** |

---

## 二、怎么发现的

查一条 `rank=-1` 的问法：

```
问：在抗洪里救人死的是谁？
存：田晓霞是润叶堂妹，省报记者。与孙少平相恋，在抗洪采访中为救落水儿童牺牲。
```

单独测这条，`semanticScore` 应该是 0.17（"抗洪"能命中）。但实际是 **0**。

追下去发现：

```js
deterministicSummary("田晓霞是润叶堂妹，省报记者。与孙少平相恋，在抗洪采访中为救落水儿童牺牲。", 160)
// → "田晓霞是润叶堂妹，省报记者。"   ← 只有 14 个字！
```

**摘要取"首句"，而首句不含"抗洪牺牲"。**

检索只搜 `title + summary`，所以**"抗洪"这条线索在检索时等于不存在**。

---

## 三、根因链条

```
写入：正文 → deterministicSummary 取首句 → summary（14 字）
                ↓                         ↓
             detail（全文）          检索只搜这个
                ↓                         ↓
           存着，但没参与检索        关键词"抗洪"命中不了
                                          ↓
                                    rank = -1（完全找不到）
```

**摘要当索引是对的**（短、便宜、给模型看、判断值不值得翻）。
**但检索不能只看索引——索引本来就是为了省略细节而造的。**

---

## 四、修法（两层坑）

### 4.1 第一层：让 detail 参与打分

```ts
if (entry.detail) {
  const detailScore = semanticScore({ title: '', summary: entry.detail, ... }, queryTokens)
  if (detailScore > 0) score += detailScore * 0.55   // ← 关键
}
```

### 4.2 第二层：**必须用加法，不能用乘法**

第一版写成：

```ts
score *= 1 + detailScore * 0.45   // ✗ 无效
```

**为什么无效**：base 分是 **0**（摘要完全不含查询词），
而 `0 × 1.077 = 0`。**乘法救不回一个零。**

改成加法 `score += detailScore * 0.55` 后，效果是 **55% → 83%**。

> 这是一个非常容易犯的错：**给"可能为零"的量做比例加成，等于什么都没做。**

---

## 五、为什么系数是 0.55

| 系数 | 含义 | 实测 |
|---|---|---|
| 太低（0.2） | 正文命中几乎不加分 | 救不回 |
| **0.55** | 正文命中能救回，但压不过 title 精确命中 | **55% → 83%** |
| 太高（1.0） | 长正文的条目靠"命中一堆常见词"作弊 | 会伤含名问法 |

0.55 是"能救回但不喧宾夺主"的位置。含名问法仍保持 100%。

## 六、这一轮其他机制的真实贡献（A/B，40 条不含名问法）

| 机制 | top1 | 判定 |
|---|---|---|
| 基线（全关） | 50% | — |
| 称谓消解 | 57% | ✓ +7pt |
| 关系一跳 | 55% | ✗ −2pt（但跨实体唯一手段，保留） |
| 意图类型加权 | 53% | ✗ 已关（`USE_KIND_BOOST = false`） |
| 唯一特征 | 53%（top3 68%） | ◐ 召回 +3pt |
| **detail 参与检索** | **83%** | **✓✓ +30pt（本轮突破）** |

**注意：detail 那一项是在前几项都打开的基础上测的。**
单独关掉 detail 会掉回 55% 左右。

## 七、顺带修掉的另一个过度过滤

`CN_FUNCTION_CHARS` 曾包含方位字（`上中下里前后`），导致：

```
tokenize("那个在煤矿下井的年轻人是谁") → 12 个 token
过滤后                              → 只剩 3 个
```

**「下井」被丢掉了** —— 它是这部小说的核心场景词。

修掉后保留 5 个，top3 召回 +3pt。

> **过度过滤比不过滤更坏**：它悄悄扔掉关键线索，而分数看起来还正常。

---

## 八、教训（最重要的一条）

**摘要和检索是两个不同的东西。**

- 摘要为**人/模型**服务：短、能一眼看懂、判断值不值得翻
- 检索为**匹配**服务：必须能看到全部内容，否则等于主动丢线索

我最初为了"省空间"让检索只看摘要，结果把 33% 的记忆变成了**查不到的记忆**。

**存下来的东西，如果检索看不到，等于没存。**
