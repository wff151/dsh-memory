# 称谓消解 · 实测报告

> 目标：消灭检索里那 27% 的「找不到」——它们全是**代词 / 称谓 / 间接说法**造成的。
> 时间：2026-10-25

---

## 一、结论

| 指标 | 改前 | 改后 | 变化 |
|---|---|---|---|
| top1 命中 | 60% | **77%** | **+17pt** |
| top3 召回 | 73% | **90%** | **+17pt** |
| 完全找不到 | 27% | **10%** | **−17pt** |

**改动很小（一个纯函数模块），效果是这三轮里最大的。**

代词部分另测：6 步对话流里，**3 条带代词的问题靠"话题"救回**（无话题时全部 MISS）。

---

## 二、三类失败，三种解法

原始失败 8 条，按病根分三类：

| 类型 | 例子 | 解法 | 效果 |
|---|---|---|---|
| **称谓 / 身份** | 「**嫂子**身体怎么了」<br>「**哥哥**办厂为什么破产」<br>「矿上那个**寡妇**是谁」 | 词表扩展（纯函数） | **全部修好** |
| **代词** | 「**他**后来在矿上怎么样」<br>「**她**最后怎么样了」 | 需要"当前话题" | **3/3 救回**（有话题时） |
| **间接描述** | 「**砖窑**那事后来怎么了」<br>「**车祸截肢**的是谁」 | **不需消解**——这些词就在正文里 | 仍失败，是**打分**问题不是消解问题 |

## 三、实现

### 3.1 模块 `anaphora.ts`

两个能力，分开设计（因为依赖不同）：

```
expandKinshipAndRole(query)  → 不需要上下文，纯词表
resolvePronoun(query, topic) → 需要"当前话题"才能消解
```

**词表覆盖**（只收录高频、无歧义的）：

| 类别 | 词 → 扩展成 |
|---|---|
| 亲属 | 嫂子→妻/媳妇/老婆 · 哥哥→兄/之兄 · 叔叔→叔 · 妹妹→妹 |
| 身份 | 当兵的→军人/兵/复员 · 当老师的→教师/教书 · 寡妇→遗孀/矿难 · 矿工→下井/煤矿 |

**代词**只处理 `他/她/它/他们/她们`，并特意排除「其**他**」这种误判。

### 3.2 关键设计决定：**只扩查询，不改条目**

消解是**在查询侧**做的：把「嫂子身体怎么了」扩展成
`嫂子身体怎么了 + 妻 + 媳妇 + 老婆`，然后拿这些词去匹配。

**为什么不在写入时做**：
- 写入时不知道将来会怎么问
- 改条目会污染存储（同一件事有多种表述就多条记忆）
- 扩查询是**无副作用**的，错了最多是没帮上，不会写坏数据

### 3.3 话题怎么来（关键，也是局限）

代词需要"刚才聊的是谁"。当前实现：

```
inferTopicFromRecent(store) → 取最近一条带 title 的短期记忆
```

**判据刻意克制**：title ≤ 12 字、无问号才算。取不到就返回 `null`，
检索按原样处理 —— **宁可不消解，也不硬猜一个错的话题**。

> 猜错话题比不消解更坏：会把「他」替换成无关实体，让检索跑偏。

## 四、代词消解的实测（对话流）

6 步对话，每步先建立话题再问：

| 问题 | 类型 | 无话题 | 有话题 |
|---|---|---|---|
| 孙少平在煤矿过得怎么样 | 直接 | ✓ | ✓ |
| **他**后来还干过别的吗 | 代词 | **MISS** | **✓ 命中** |
| **他**喜欢的那个姑娘是谁 | 代词+跨实体 | MISS | ✗（命中孙少平而非田晓霞） |
| **她**最后怎么样了 | 代词 | **MISS** | **✓ 命中** |
| **他**弟弟叫啥 | 代词+跨实体 | MISS | ✗（命中孙少安而非孙少平） |
| **他**出什么事了 | 代词 | **MISS** | **✓ 命中 1.00** |

**3 条救回，2 条失败。**

失败的两条有个共同点：**答案不是话题本身**——
问「他喜欢的姑娘」答案应该是田晓霞，问「他弟弟」答案应该是孙少平。
**代词消解只能指向"话题这个人"**，指不到"话题的关系人"。

那需要的是**关系图**（谁爱谁、谁是兄弟），不是代词消解。见 §6。

## 五、顺带修掉的两个 bug

### 5.1 短期检索不搜摘要

```ts
// 改前
semanticScore({ title: item.content, summary: item.content }, tokens)
// 改后
semanticScore({ title: item.title ?? item.content,
                summary: `${item.summary ?? ''} ${item.content}` }, tokens)
```

改前**摘要完全没用上**（而投影用的就是摘要）。现在正文 + 摘要 + 标题都参与匹配。

### 5.2 分数离散导致的 50% 并列

`semanticScore` 原来是纯整数比（命中数/token 数），只有 14 个可能值。
改成加连续项：

- **过滤跨词垃圾片**：`到孙`/`安那` 这类跨虚词拼出的 bigram 不计入分母
- **长度加权**：4 字片段 > 2 字 bigram
- **位置加权**：title 前部 > 后部 > 仅正文

**效果**：top1 并列率 **50% → 20%**。

> 注：这一项单独做的测试显示 top1 没提升（60% → 60%），
> 说明**并列不是主因，称谓才是**。但并列降到 20% 对稳定性有好处，保留。

## 六、还剩下的 10%

| 类型 | 例子 | 需要什么 |
|---|---|---|
| **跨实体推理** | 「他喜欢的姑娘是谁」 | **关系图**（谁爱谁/谁是兄弟/谁是父亲） |
| **纯事件描述** | 「砖窑那事」→ 孙少安 | 更好的打分（事件词 → 人物关联） |

这两项都不是"消解"能解决的，是**知识结构**问题。

## 七、与 embedding 方案的对比（回答易用性问题）

| | 称谓消解 | 向量检索 |
|---|---|---|
| 需要额外服务 | **不需要** | 需要 llama.cpp/LM Studio + 模型 |
| 用户要做什么 | **什么都不用** | 装模型、起服务、配端口、配前缀、调阈值 |
| 装完即用 | **是** | 否（服务不开就静默回退） |
| 本次实测收益 | top1 **+17pt** | 正确文档胜出 **2/6**（弱） |
| 代码量 | 一个 ~120 行纯函数模块 | 改 3 个文件 + 配置 3 项 |

**结论：称谓消解在"易用性"和"收益"上都胜出。**

向量检索的定位应该是**锦上添花**（服务在就多一个信号，不在就回退），
不该作为主方案 —— 它对普通用户来说门槛太高（要先装对模型、起对端口）。

**这也回答了你提的"子 agent 方案"**：子 agent 同样需要**额外启动一个模型**，
易用性上和 embedding 一个量级，但收益更不确定。**不如先把纯代码的部分做满。**
