# EPERM：手动衰减写回失败（2026-10-27）

> 现象：`brain_memory_decay` 每次都报
> `EPERM: operation not permitted, rename '....tmp' -> 'brain_memory.json'`
> 而定时衰减（每 6 小时）看起来也在静默失败。

---

## 一、根因（已实证）

**不是权限问题，不是磁盘问题，是 Windows 的文件共享语义。**

DSH 的 storage 用「写临时文件 → fsync → rename 覆盖」做原子替换
（`@deepseek-ai/dsh-storage-json` 的 `writeAtomic`）。
在 Windows 上 `rename` 映射到 `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`，
**只要目标文件当前被任何句柄以"读且不允许删除共享"的方式打开，就会失败**。

实测复现（`_tools/test-write-conflict.mjs`）：

| 场景 | 结果 |
|---|---|
| 目标文件被一个**读句柄**持有 | **失败 `EPERM`** |
| 两个写入并发 | 成功 2/2 |
| 独立进程、无人持有 | 成功 |

所以：**宿主在读 `brain_memory.json` 的时候，插件写不回去。**

这解释了三个现象：
1. 手动衰减必然失败 —— 手动触发时宿主正在正常服务，几乎总在读该文件
2. 独立 Node 进程测试能成功 —— 那里没有别的读句柄
3. 定时衰减也在失败 —— 只是它的错误被 `catch` 记成 warn，不容易看到

---

## 二、影响范围

| 功能 | 是否受影响 |
|---|---|
| 读记忆（检索、注入） | 不受影响 |
| 写新记忆（record / short / note） | **也可能受影响**（同一个 writeAtomic） |
| 短期衰减归档 | **受影响** |
| 容量上限裁剪 | **受影响** |

**注意**：写新记忆平时看起来没事，是因为写入发生在宿主读的间隙里；
赶上冲突时同样会 EPERM。

---

## 三、可选修法

### 方案 A：重试 + 退避（改动最小，推荐先做）

`writeAtomic` 遇到 `EPERM` / `EBUSY` 时，等几十毫秒重试几次。
Windows 上读句柄通常是**短时的**（读一次就关），退避后大多能成功。

代价：最坏情况写入延迟增加几百毫秒；不影响正确性。

### 方案 B：插件侧改用「读-改-写」而不是整表替换

只在必要字段上写，减少写入体积与持有时长。但**根治不了** —— 仍要 rename。

### 方案 C：换存储后端（SQLite）

DSH 有 `dsh-session-query-sqlite` 之类的后端。SQLite 用自己的事务与锁，
不存在"读句柄挡住 rename"的问题。但换后端是**宿主级别**的改动，插件无权决定。

### 方案 D：写之前检测冲突

先试着独占打开目标文件，失败就跳过本轮（下个周期再试）。
简单，但会**推迟**归档而不是完成它。

---

## 四、我建议的顺序

1. **先做 A**（重试退避）—— 一行改动，能覆盖多数情况
2. 观察是否还有稳定失败
3. 如果仍然频繁，再考虑 C（换后端，需要宿主支持）

**不建议**只做 D：跳过写入会让"衰减"看起来正常但其实什么都没做，
和之前那个「权重从没写回」的 bug 是同一类欺骗。

## 六、修法（已实施，待重启验证）

在插件侧做了两层改动（`src/store.ts`）：

### 6.1 表级写重试（`guardTable`）

`store.ts` 里有 **24 处** `tables.xxx.put/delete`。
逐个包一层既啰嗦又容易漏，所以**在表句柄上包一层 Proxy**——
`put` / `delete` / `update` 遇到 `EPERM` / `EBUSY` / `EACCES` 就退避重试，
其余方法（`get` / `entries` / `keys` / `size`）原样透传。

退避：20 → 40 → 80 → 160 → 320ms，最多 6 次，总等待约 0.6 秒。
**非 EPERM 错误立即抛出**——不能把真问题（比如磁盘满）也吞进重试里。

依据：读句柄通常是**短时**的（宿主读一次就关），退避后大多能成功。

### 6.2 `replaceShortTerm` 跳过无变化的条目

原实现逐条删+写：删 600 条 + 写 110 条 = **约 700 次 rename**，
每次都可能撞冲突。改成：

- 只删"该 mode 下不在保留集里"的
- 写之前比对 `weight / accessCount / lastAccess / summary / title`，
  **没变就不写**

衰减时大部分条目的内容是不变的（只有权重变），这一改能省掉大量写盘。

### 6.3 测试

`_tools/test-write-retry.mjs`（9 项全过）：

| # | 验证 |
|---|---|
| 1 | 无错时直接成功（不无谓重试） |
| 2 | 失败 3 次后重试成功 |
| 3 | 持续失败会抛出（不无限重试） |
| 4 | **非 EPERM 立即抛出**（不吞真问题） |
| 5 | 退避总时长在 0.3–1.5 秒之间 |

## 七、没做的事（诚实标注）

**没有根治。** 重试只是"撞了再来"，遇到宿主长时间持有读句柄仍会失败。

真正的根治要么：

- 让宿主在写之前释放读句柄（**宿主级改动，插件无权**）
- 换成支持并发锁的后端（SQLite，**需要宿主支持**）

**当前状态**：短期库 616 条、占 32k 窗口 **83.84%**，
占比触发与容量上限**仍未生效**——因为它们都要先能写回存储。
需要重启后手动触发一次衰减来验证重试是否足够。
