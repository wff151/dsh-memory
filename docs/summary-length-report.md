# 摘要长度 · 实测与取舍

> 时间：2026-10-26
> 起因：用户看到「摘要截掉了关键信息」，问是不是摘要总结得太短。
> **答案：不是上限太小，是"取首句"太粗。**

---

## 一、先量真实数据（89 条记忆库）

| 指标 | 改前 | 改后 |
|---|---|---|
| 摘要上限 | 160 字 | 160 字（没变） |
| **实际摘要中位** | **50 字** | **107 字** |
| **填到上限 90% 的** | **12%** | **29%** |
| 摘要/原文比 | 63.8% | 77.5% |

**关键证据**：改前只有 12% 的摘要接近上限 —— **上限远远没用满**。
所以"截掉关键信息"不是上限太小，是**取首句这个策略本身太短**。

### 典型例子

```
原文 500 字 → 摘要 27 字
  「你是「游戏Agent项目」的执行层（模拟输入）实验员。」
```

**首句只是个身份标签，后面 473 字的实质内容全丢了。**

这正是「在抗洪里救人死的是谁」查不到田晓霞的同一个根因：
首句「田晓霞是润叶堂妹，省报记者。」之后才是"抗洪牺牲"。

## 二、改法：首句打底 + 按句补齐

```ts
// 旧：只取首句
return splitFirstSentence(src)

// 新：按句累加，能整句放下就放，超过上限就停
for (const s of sentences) {
  if (out.length + s.length <= maxChars) out += s
  else if (out.length >= maxChars * 0.6) break   // 够用了，不砍半句
  else return cutAtClause(out + s, maxChars)     // 还太少，补到上限
}
```

**两个细节**：
1. **不把句子砍半**：已填到 60% 以上就停，宁可短一点也不切碎句子
2. **末尾兜底截断**：只有一句的超长文本（80 字不分段）不会被循环处理，
   必须显式截。这个 bug 是单测 `maxChars 可以调小` 抓到的。

## 三、取舍：长短两档的实测

同一套 100 问（《平凡的世界》）：

| 档位 | 摘要中位 | top1 | top3 |
|---|---|---|---|
| `long` | 107 字 | **89%** | **99%** |
| `short` | 50 字 | **93%** | **99%** |

**长摘要反而让 top1 降了 4 个点。** 原因：

摘要变长 → 别的条目也能命中更多查询词 → 把正确条目挤下去。
**含名问法从 100% 掉到 95%**，就是被噪声稀释的。

**这是固有取舍，不是 bug：**

| | 长摘要 | 短摘要 |
|---|---|---|
| 摘要自己能看懂 | ✓（120–160 字） | ✗（只够判断"讲什么"） |
| top1 | 89% | **93%** |
| 上下文开销 | 100% | **约 40%** |
| 丢关键信息的风险 | 低 | **高**（首句之后全丢） |

---

## 四、决定：做成开关，默认 `long`

**为什么默认长摘要**（尽管它 top1 更低）：

**我的数据只来自《平凡的世界》一本小说。**

- 小说人物条目：首句通常就是"某某是…"，短摘要够用
- 代码/工单/聊天：首句常是标签或寒暄，**实质内容在中间**（像上面那个 27 字的例子）

**在没验证过的领域里，长摘要是更安全的选择** —— 它至少不会把关键信息丢掉。
短摘要省上下文，但省的那部分正是可能救命的部分。

### 配置

```yaml
summaryLength: long    # 默认。120–160 字，摘要自己能看懂
# summaryLength: short # ≤60 字，上下文开销约 40%，但可能丢后置细节
```

设置页「记忆 → 摘要长度」可切换，`volatile()` 改完即生效。

---

## 五、"短摘要省多少上下文"的准确说法

**省的不是总上下文，是长期记忆条目里的 `summary` 字段。**

实测比例：

| | 字数 |
|---|---|
| long 摘要 | 143 字（示例） |
| short 摘要 | 57 字 |
| **比例** | **short = long × 40%** |

**但要注意**：`summary` 只在**检索命中后**才进上下文（一次 top3 约 3 条）。
每步自动注入的部分（小黑板 + 短期投影 + 画像）**不受这个开关影响**。

所以这个开关的实际收益：
- 检索命中时：每次省约 60% 的摘要字数
- 没命中时：**完全不影响**

**它不是"省上下文"的主要手段** —— 主要手段是注入按条数截断（见 README §6）。

## 六、教训

**"摘要截掉了关键信息"的正确修法不是"把摘要加长"，是"让检索不只看摘要"。**

我已经在上一轮做了后者（`detail` 参与打分，top1 55% → 83%）。
这一轮加长摘要，top1 反而从 93% 掉到 89%。

**两件事不要混：**
- 摘要要短（给模型看，判断值不值得翻）
- **检索要看全文**（否则等于主动丢线索）

加长摘要治不了"查不到"，只能治"摘要本身不好读"。
